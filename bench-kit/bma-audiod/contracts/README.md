# BMA interface contracts

A contract here is a machine-readable, versioned description of one interface between two components of the BMA
pipeline (a file, a UDP datagram, a byte stream, an HTTP API), together with example data and a conformance test that
fails when producer or consumer drifts from it. Prose that is not backed by a schema or an exact byte table and a test is
not a contract.

```
contracts/
  README.md            this policy
  CHANGELOG.md         every contract version, and known disagreements between code, docs and real data
  changelog.d/         one fragment per new changelog entry (`<interface>.md`); counted like CHANGELOG.md, so parallel pull requests do not collide
  specs/               one human spec per interface (header: `contract:` and `contract_version:`)
  schemas/             JSON Schema (draft 2020-12) for the JSON interfaces; `x-contract-version`, `$id` urn:bma:contract:<name>
  fixtures/            small sanitized examples (<= 50 lines per file, no audio, no coordinates), regenerated by tools/make_fixtures.py
  ref_binary.py        reference parser/builder for the binary layouts (BMAA, BMD1, BMAS), independent of the production code
  check_contracts.py   the checker (fixtures always, the live files with --live)
  test_contracts.py    conformance tests, including mutation proofs
```

Run `python check_contracts.py` (hermetic) or `python check_contracts.py --live` (adds the last 2000 lines of every live
file under `<data-dir>`). Exit code 1 and a `DRIFT <file>:<where> [<kind>] <json path>: <message>` line per finding
mean a component and its contract disagree. The validators need `jsonschema` and `numpy` (any venv with both).

## Versions

* Every interface has its own `contract_version`, `MAJOR.MINOR.PATCH`. It lives in the schema (`x-contract-version`) and in the
  spec header; the checker fails if they differ or if CHANGELOG.md has no `<interface> <version>` line.
* Records and files do not carry the version today (the producers cannot change in step). New producers SHOULD add a
  `contract_version` field to status-style objects; JSONL records stay unversioned and are versioned by the file.
* MAJOR: a breaking change. MINOR: an additive change. PATCH: a clarification or a fix that makes the schema describe what
  the producer really does, without accepting or rejecting anything new that a conforming producer emits.

## Compatibility rules

1. Within a major version changes are ADDITIVE ONLY: new optional fields, new record kinds, new enum values, new flag bits.
   Never remove, rename, retype or tighten an existing field, and never change its meaning or unit.
2. Receivers MUST ignore unknown fields, unknown record kinds (they skip the record) and unknown flag bits, and MUST treat
   an unknown enum value as the most conservative known one (for example `state` other than `ok` is not ok). The schemas
   therefore do not forbid extra properties.
3. A producer MUST NOT start emitting a new field, kind or enum value before the contract lists it. The checker enforces
   this on live data: an unknown record kind is drift.
4. A breaking change is a new MAJOR: the new layout gets a new identifier (`BMAA` version byte, `/v2` path, new schema `$id`
   suffix) and is produced alongside the old one for the deprecation window below. Receivers choose by that identifier.
5. Deprecation window: a deprecated interface or field keeps working, and keeps being produced, for at least 90 days and
   until every known consumer in this repository has moved. The CHANGELOG records the date it was deprecated.

## Required process

A change to a producer (code that writes the file, packet or response) MUST change, in the same commit: the schema or byte
table, the spec, the fixtures, the conformance tests, the version, and CHANGELOG.md. A pull request that changes a producer
and not these is incomplete. When real data disagrees with the contract, the contract is fixed (PATCH) or the producer is
fixed, and the disagreement is written in the CHANGELOG; it is never silently ignored. A known defect is pinned by an
expected-failure test (it must fail until the defect is fixed, then the test is removed), never by a test that accepts it.

Ownership: the producer's owner owns the contract of what it emits. Today that is the BMA pipeline owner for every
interface, and the dspd service owner for the dspd HTTP API.

## HTTP APIs (dspd and any future service)


* Path-versioned: all routes under `/v1`; a breaking change is `/v2` served alongside `/v1` for the deprecation window.
* The OpenAPI `info.version` is the contract version and follows the rules above.
* Errors are RFC 9457 `application/problem+json` (`type`, `title`, `status`, `detail`, `instance`) plus a stable
  machine-readable `code` extension member that clients branch on; `code` values are part of the contract and are never reused.
* Timestamps are RFC 3339 UTC (`2026-10-24T19:30:00Z`).
* Bearer-token authentication on every route except a minimal unauthenticated `/v1/health`.
* Every mutating call accepts an `Idempotency-Key` header; replaying a key returns the original response and does not repeat
  the action on the hardware.
* No secrets and no coordinates in any response body, log line or problem detail. Positions are never finer than county level
  anywhere in this project.
* Anything that writes to the board (DSP vectors, FPGA registers, reboots) is a dry run by default and executes only with an
  explicit opt-in in the request; the deny-list of dangerous operations (for example DSP vector `0x3A`, which resets the
  board) is enforced by the server and reported with a stable `code`.
* The service documents the effect of every write, its reply, and how to roll it back.

## Adding an interface

Write the schema (or byte table) and spec, add fixtures (build them with tools/make_fixtures.py so they stay reproducible),
register the schema, spec and fixtures: for an analyzer plugin in its entry of `analysis/plugins.manifest.json` (`contract`; see `analysis/README.md`, "Adding a plugin"), for any other interface in `check_contracts.py` (the dictionaries at the top), add the tests (exact values,
a positive twin for every negative case, and a mutation proof), and add the CHANGELOG line, all in one commit.
